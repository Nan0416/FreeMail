# CORS verification (#47) — run this on the first real deploy

FreeMail's browser↔API security depends on behavior of **API Gateway v2 managed CORS**
that cannot be observed from a CDK synth or a unit test. The security review approved the
managed-CORS approach ("Option A") **conditionally**: these claims are _to be proven at
implementation, not established facts_.

**Until this checklist passes on a deployed stack, the CORS design is unverified.**

Run every probe below after the first `cdk deploy`. Record the results in the #47 thread.

## Why this matters

The SPA's access cookie is `HttpOnly`, so the app cannot see when it expires. It relies on
receiving a **readable** 401/403 from the authorizer to know it should refresh and retry
(`packages/web/src/api/client.ts`). An authorizer denial is generated by API Gateway
**before** the integration Lambda runs, so no code of ours can attach CORS headers to it.
If managed CORS does not decorate that response, the browser cannot read it, `fetch`
throws, and transparent refresh breaks.

## Setup

```sh
APP=https://app.example.com     # appDomain
API=https://api.example.com     # apiDomain
```

## 1. Readable authorizer denial — **the deciding probe**

```sh
curl -si "$API/me" -H "Origin: $APP" -H "Cookie: __Host-fm_access=expired.or.bogus" \
  | grep -i 'access-control-allow-origin\|^HTTP/'
```

**Pass:** a 401/403 **carrying** `access-control-allow-origin: https://app.example.com`.

**Fail → Option A is rejected.** Move cookie validation out of the Lambda authorizer into
the integration handler so denials originate from our own Lambda, and emit CORS headers
there. This is a significant reshape of the auth path — raise it before proceeding.

## 2. Bad-origin withholding

Run each against a preflight, a success path, and an error path:

```sh
for ORIGIN in "https://evil.com" "https://evil.example.com" "null" "not-a-url" \
              "https://app.example.com, https://evil.com"; do
  curl -si -X OPTIONS "$API/auth/login" \
    -H "Origin: $ORIGIN" \
    -H "Access-Control-Request-Method: POST" \
    -H "Access-Control-Request-Headers: content-type" \
    | grep -i 'access-control-allow-origin\|access-control-allow-credentials\|^HTTP/'
done
```

**Pass:** **no usable** `access-control-allow-origin` / `-allow-credentials` for any of
them. Note the same-site sibling (`evil.example.com`) and the comma-separated duplicate
specifically — those are the two that matter most.

**Note:** "withhold CORS authorization" ≠ "reject the request". The request itself should
still reach the authorizer; only the CORS headers are absent. Do **not** treat a 200/403
as a failure here — check the headers.

## 3. `Vary: Origin` on every origin-dependent response

Check preflight, integration success, authorizer denial, and a gateway 4xx:

```sh
curl -si -X OPTIONS "$API/auth/login" -H "Origin: $APP" \
  -H "Access-Control-Request-Method: POST" | grep -i '^vary'
curl -si "$API/me" -H "Origin: $APP" -H "Cookie: __Host-fm_access=bogus" | grep -i '^vary'
curl -si "$API/nope" -H "Origin: $APP" | grep -i '^vary'
```

**Pass:** `vary: origin` present on each.

**Partial fail (only `Vary` missing):** either add it at a layer we control, **or**
demonstrate the emitted `ACAO` is origin-independent/static, such that no cache can serve
an allowlisted-origin variant to a different origin. Document which.

## 4. No-`Origin` agent path is unaffected

```sh
curl -si -X POST "$API/mcp" \
  -H "x-api-key: $FREEMAIL_API_KEY" \
  -H "content-type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | head -1
```

**Pass:** 200. CORS governs browsers only; an agent call carries no `Origin` and must
behave exactly as it did before #47.

## 5. Bodyless CSRF gate rejects before any state change

```sh
curl -si -X POST "$API/auth/refresh" -H "content-type: text/plain" \
  -H "Cookie: __Host-fm_refresh=$REAL_REFRESH_TOKEN" | head -1
```

**Pass:** `415`, **and** the refresh token still works afterward — the rejection must
happen before rotation. (Unit-tested in `packages/service/tests/handlers/rest.test.ts`;
this confirms it end-to-end.)

## 6. End-to-end browser check

In a real browser at `$APP`: sign in, let the access cookie expire (15 min) or clear it,
then trigger any authenticated action. The SPA should transparently refresh and retry with
no visible error. This is probe 1 observed from the app's own perspective.
